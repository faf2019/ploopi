== Module DBREPORT - version 2.1.9 ====================================================

2026-10-12  Ovensia <stephane@ovensia.fr>

* Aperçu SQL : coloration par classes (thème clair ou sombre de ploopi4) au lieu de
  styles en ligne sur fond blanc forcé, défilement borné, bouton « Copier la requête ».
  La requête, déjà en UTF-8, était retranscodée deux fois : les accents s'abîmaient.
* Content-Security-Policy stricte : écrans déclarés prêts (_DBREPORT_CSP). Plus aucun
  gestionnaire en ligne ni URL javascript: — fenêtres par data-ploopi-topopup,
  confirmations par data-ploopi-confirm, cases du choix du format par
  ploopi_checkbox_zone, listes et boutons par les actions de include/functions.js
  (ploopi.actions.dbreport_*), script du graphique avec le nonce.
* Sélecteurs de couleur du graphique rétablis : ils s'installaient par la classe
  « color {…} » de jscolor 1, que jscolor 2.5 ne reconnaît plus (champs texte nus) ;
  data-jscolor en JSON strict.
* Choix d'une fonction SQL : ploopi.insertatcursor (alias historique abandonné).
* Création d'une requête, d'un champ, d'une table ou d'une relation : en SQL strict
  (défaut de MariaDB), l'INSERT échouait sur la première colonne NOT NULL sans défaut
  (ws_id, function_group…), sans message — aucune requête ne pouvait être créée. Les
  colonnes absentes sont complétées par leur valeur par défaut (dbreport::defaults).
* Clonage : les relations n'étaient pas copiées (INSERT … SELECT sans type_join) ; les
  champs non plus (function_group manquant).
* Graphique dont les valeurs viennent d'un champ texte : page d'erreur (TypeError en
  PHP 8) ; valeurs converties en nombres, comme pour les données tracées.
* Ajout de champs : inclusion de include/classes/mb.php, disparu (avertissement).

== Module DBREPORT - version 2.1.2 ====================================================

2026-10-08  Ovensia <stephane@ovensia.fr>

* Correctif : l'affichage d'un graphique finissait en erreur fatale.

  En remplaçant utf8_encode() (dépréciée en PHP 8.2), la PR #63 avait laissé
  treize appels à mb_convert_encoding() sans encodage cible : ArgumentCountError
  au rendu de tout graphique. Les appels retrouvent l'équivalent exact de
  utf8_encode() (ISO-8859-1 vers UTF-8), comme les autres sites du fichier.

* Compatibilité PHP 8.1 à 8.4 (PR #63) : utf8_encode()/utf8_decode()
  remplacées par mb_convert_encoding(), garde safe_mode retirée.

== Module DBREPORT - version 2.1.1 ====================================================

2026-10-06  Ovensia <stephane@ovensia.fr>

* Sécurité : les opérations ne s'appliquent qu'aux requêtes accessibles.

  Les opérations recevaient l'identifiant d'une requête (directement, ou par l'un de
  ses champs ou l'une de ses tables) sans contrôler à quelle requête il menait :
  - tout utilisateur du module exportait ou exécutait la requête d'une autre
    instance ou d'un autre espace, donc en lisait les données ;
  - un gestionnaire de requêtes modifiait ou supprimait les requêtes d'une autre
    instance, et les requêtes verrouillées sans l'action de verrouillage.

  Un contrôle commun, en tête d'op.php, applique la règle de la liste des requêtes :
  lecture d'une requête de l'instance courante et des espaces visibles ; écriture
  avec, en plus, l'action « gérer les requêtes » et, si la requête est verrouillée,
  l'action « verrouiller les requêtes ».
